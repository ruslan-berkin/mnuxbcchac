```

web/                     Next.js (App Router, TypeScript, Tailwind, gsap) со статическим экспортом (output: "export")
  app/page.tsx           лендинг
  app/app/page.tsx       платформа (/app)
  components/…           секции лендинга, ноутбук, платформа, чат
server/
  main.py                FastAPI: /api/* + раздача web/out как статики
  jobs.py                очередь прогонов (1 воркер), статусы, TTL
  ratelimit.py           лимиты по IP и глобальные
Dockerfile               multi-stage: node build → python runtime
render.yaml              blueprint для Render (free web service, Docker)
```

Один контейнер, один сервис, один домен — без CORS.

## 4. Платформа `/app`

Сетка на десктопе: **документ | замечания и аналитика | чат**. Сверху панель.

- **Верхняя панель**: «Загрузить документ», «Пример: документ организаторов» (мгновенно из `reports/report.json`, без LLM),
  степпер прогона (нарезка → проверка требований → проверка набора → сверка цитат → верификация → отчёт),
  вердикт-бейдж, «Скачать .md / .json».
- **Документ** (слева): текст документа построчно с номерами строк. Цитаты замечаний подсвечены цветом серьёзности.
  Клик по замечанию → скролл к строке и вспышка подсветки; клик по подсветке → замечание в центре.
- **Замечания и аналитика** (центр), вкладки:
  «Сводка» (вердикт, счётчики по серьёзности и критериям, «что исправить первым»),
  «Замечания» (фильтры: серьёзность, критерий, требование; карточка: критерий с кодом, цитата, место, проблема, как исправить),
  «Требования» (таблица нарезки R-xx ↔ ID в документе).
- **Чат с агентом** (справа) — главная фишка:
  1. Агент открывает чат сам: «Я проверил документ. Чтобы его можно было отдавать в разработку, мне нужны ответы на
     N вопросов» — и выдаёт **топ блокирующих вопросов** (из критичных и сквозных замечаний), каждый с вариантами ответа
     кнопками, если вопрос «A или B?», и ссылкой на `D-xxx`.
  2. Пользователь может отвечать (кнопкой или текстом) **и** спрашивать свободно: «почему D-013 критично?»,
     «перепиши Ф-3 так, чтобы не было противоречия», «какие требования нельзя протестировать?».
     Ответы агента опираются только на отчёт и документ, ссылаются на `R-xx`/`D-xxx` (ссылки кликабельны → подсветка).
  3. Кнопка **«Перепроверить с ответами»** → агент пересматривает только затронутые замечания → у каждого статус
     «закрыто / частично / осталось» с причиной → **вердикт «было → стало»** (считает код) крупно в чате и в сводке.
  Ответы стримятся (SSE). История чата — в памяти страницы + `sessionStorage` (в try/catch).
- Мобильная версия: вкладки «Документ / Замечания / Чат».

## 5. Бэкенд (FastAPI)

| Метод | Что делает |
|---|---|
| `POST /api/runs` | multipart-файл → проверка типа/размера → задача в очередь → `{run_id}`. 429 при лимите. |
| `GET /api/runs/{id}` | `{status, stage, stages_done, error?}`; при готовности — `report` (JSON) и `document` (строки) |
| `GET /api/example` | готовый `reports/report.json` + строки примера, без LLM |
| `GET /api/runs/{id}/report.md` · `.json` | скачать |
| `POST /api/chat` | `{run_id|example, messages, answers}` → SSE-стрим ответа |
| `POST /api/recheck` | `{run_id|example, answers}` → статусы замечаний + вердикт было/стало |
| `GET /api/health` | для прогрева перед демо |

- Прогон в фоне, **1 воркер**, очередь с позицией («вы в очереди: 2»). Прогресс — через колбэк `on_stage` (см. §6).
- `pipeline.run(..., limits=Limits.web(), display_name=<имя файла>, cache_namespace=<run_id>)`, отдельная временная
  папка на прогон; загруженный файл удаляется после прогона; результаты живут 2 часа (TTL), потом чистятся.
- **Лимиты (платный ключ!)**, все через env:
  `SITE_LIVE=1` (0 → живые прогоны выключены, работает только пример и чат по примеру),
  `SITE_DAILY_RUNS=5` (на весь сайт), `SITE_RUNS_PER_IP=1`/сутки, `SITE_CHAT_PER_IP=40`/сутки,
  `SITE_RECHECK_PER_IP=5`/сутки, `SITE_MAX_CHAT_TOKENS` на ответ. При превышении — понятное сообщение
  и предложение открыть пример. IP — из `X-Forwarded-For` (Render за прокси), первый адрес.
- Ключ только в переменных окружения Render. На фронт не уходит ничего, кроме результатов.
- Render free: 512 МБ — выставить `REQCHECK_PARSE_MEMORY_MB=384`; сервис засыпает — перед демо дёрнуть `/api/health`.

## 6. Доработки ядра (`reqcheck`, с тестами на fake LLM)

1. `pipeline.run(..., on_stage: Callable[[str], None] | None = None)` — вызывается при входе в этап
   (`ingest, segment, check_each, check_set, ground, verify, render`). Без колбэка поведение не меняется.
2. `reqcheck/chat.py` + `prompts/chat.md`: ответ на сообщение пользователя по отчёту и документу.
   Документ и отчёт — **данные** (`<document>`, `<report>`), инструкции внутри игнорируются. Ответ ссылается на
   `R-xx`/`D-xxx`; цитаты из документа в ответе проверяются `ground` — не найденная цитата вырезается.
   Стриминг через провайдера (для `openai_compat` — `stream=True`; если провайдер не умеет — отдать целиком).
3. `reqcheck/questions.py`: функция `top_questions(report, n=10)` — блокирующие вопросы: сначала критичные и
   затронувшие больше требований, по одному на тему, с вариантами ответа, если вопрос альтернативный.
   **Тот же топ вывести в начале раздела 5 отчёта** («Главные вопросы»), полный список — ниже.
4. `reqcheck/recheck.py` + `prompts/recheck.md`: `recheck(report, document, answers) -> RecheckResult` — LLM
   пересматривает **только замечания, к которым есть ответы**: `resolved | partial | open` + причина; новый
   вердикт считает код по тем же правилам. CLI: `python -m reqcheck IN OUT --answers answers.md` (формат: `D-013: ответ`).
5. Всё новое — под тем же бюджетом (`BudgetedLLM`) и с тестами.
