## 1. Что делает агент

Агент получает документ с требованиями (PDF обязательно, также DOCX/MD/TXT).
Он выделяет отдельные требования, проверяет каждое и весь набор по ISO/IEC/IEEE 29148:2018
(п. 5.2.5, 5.2.6) и IEEE 830-1998 (п. 4.3) и записывает отчёт на русском в файл.

Запуск одной командой:

```
python -m reqcheck <путь_к_требованиям> <путь_к_отчёту.md>
```

Рядом с отчётом всегда пишутся `<отчёт>.json` (те же данные, машиночитаемо) и `<отчёт>.log`.

## 2. Как оценивает жюри (держи в голове при каждом решении)

Четыре критерия, по 25% каждый:
1. **Уточняющие вопросы**: агент задаёт нужные вопросы по ТЗ. Это отдельный, заметный раздел отчёта.
2. **Архитектура**.
3. **Ценность**: качество продукта и отчёта.
4. **Презентация и защита**.

## 3. Главный принцип: «LLM думает, код контролирует»

LLM только **находит** дефекты и **формулирует** замечания и вопросы.
Всё остальное делает детерминированный код:
- структура отчёта (Jinja2-шаблон, а не текст модели);
- счётчики, сводка, вердикт «можно ли начинать разработку»;
- паспорт прогона (дата, модель, коммит, SHA-256 входного файла);
- проверка того, что каждая цитата действительно есть в документе.

### Конвейер

```
ingest → segment → check_each → check_set (+ lint) → ground → render
```

| Этап | Модуль | Суть |
|---|---|---|
| ingest | `reqcheck/ingest.py` | PDF (`pymupdf`), DOCX (`python-docx`), MD/TXT → `Document` с блоками и якорями (страница, раздел, номер строки). Пустой текст (скан) → ошибка с кодом выхода 3, а не пустой отчёт. |
| segment | `reqcheck/segment.py` | Явные ID (`Ф-1`, `НФТ-2`, `FR-3`, `REQ-…`) ищутся регулярками. Остальные требования (НФТ, данные, интеграция, критерии приёмки, правила API, статусы) выделяет LLM. У каждого требования **обязательна дословная цитата**. Наш ID `R-01…`, исходный ID или «без номера». |
| check_each | `reqcheck/checks/each.py` | Один вызов LLM на требование (или батч из ≤5). В промпт идут контекст раздела и закрытый список кодов критериев. |
| check_set | `reqcheck/checks/set.py` | Перекрёстные проверки: ФТ ↔ критерии приёмки, основная часть ↔ дочерняя спецификация/API, данные ↔ API, НФТ ↔ цели, UI ↔ API. Плюс полнота: чего не хватает. |
| lint | `reqcheck/checks/lint.py` | Правила **без LLM** (см. §6). Работают всегда, в том числе без ключа. |
| ground | `reqcheck/ground.py` | Каждая цитата нормализуется (регистр, пробелы, кавычки, ё/е, неразрывные пробелы) и ищется в исходнике (точное совпадение, затем fuzzy через `rapidfuzz` ≥ 90). Цитата не найдена → замечание отбрасывается и пишется в лог и в счётчик «отброшено». Затем дедупликация и нормализация серьёзности. |
| render | `reqcheck/render.py` + `templates/report.md.j2` | Сборка отчёта. |

## 4. Модель данных (pydantic, `reqcheck/models.py`)

```python
class Anchor:      section: str; page: int | None; line_start: int; line_end: int
class Requirement: id: str            # R-01
                   source_id: str | None   # "Ф-1" или None
                   kind: Literal["functional","nonfunctional","data","integration",
                                 "acceptance","api","ui","other"]
                   quote: str              # дословно из документа
                   summary: str            # краткая формулировка
                   anchor: Anchor
class Finding:     id: str            # D-001
                   scope: Literal["requirement","set"]
                   requirement_ids: list[str]
                   criterion: CriterionCode
                   severity: Literal["critical","major","minor"]
                   quotes: list[str]       # каждая проходит ground
                   anchors: list[Anchor]
                   problem: str            # что не так, конкретно
                   fix: str                # как исправить
                   question: str | None    # уточняющий вопрос аналитику
                   source: Literal["llm","lint"]
class RunPassport: document_title, document_path, document_sha256, run_datetime,
                   model_provider, model_id, agent_version (git describe --tags --dirty),
                   llm_mode: Literal["full","lint-only"]
class Report:      passport, requirements, findings, dropped_count, verdict
```

Каждый ответ LLM валидируется по схеме. Если JSON невалиден, делается один повторный запрос
«исправь по схеме» с текстом ошибки. Если и он не прошёл, этап для этого требования помечается
`failed` и попадает в отчёт как «не проверено» (не молча).

## 5. Критерии (закрытый список кодов, `reqcheck/criteria.py`)

**Отдельное требование (29148 п. 5.2.5 + IEEE 830 п. 4.3):**
`NEC` необходимое · `APP` уместное / без лишних проектных решений · `UNA` однозначное ·
`CMP` полное · `SNG` единичное · `FEA` выполнимое · `VER` проверяемое ·
`COR` корректное · `CNF` соответствует шаблону/стандарту

**Набор (29148 п. 5.2.6 + IEEE 830 п. 4.3):**
`S-CMP` полный · `S-CON` непротиворечивый · `S-FEA` выполнимый · `S-CMH` понятный ·
`S-VAL` валидируемый · `S-RNK` ранжирован по важности/стабильности ·
`S-MOD` модифицируемый · `S-TRC` трассируемый

Для каждого кода в `criteria.py` хранятся название, ссылка на пункт стандарта и одна фраза
«как проверять». Эти тексты вставляются в промпты и в приложение к отчёту.

**Серьёзность (§6 ТЗ называет критичными непроверяемые, противоречивые и неполные):**
- `critical`: `VER`, `S-CON`, `CMP`/`S-CMP`, если без исправления нельзя написать код или тест;
  противоречие между требованием и критерием приёмки или API.
- `major`: двусмысленность с несколькими разумными трактовками, отсутствующая граница или единица.
- `minor`: стиль, шаблон, оформление, незаполненные служебные поля.

## 6. Правила линтера (без LLM)

Каждое правило — отдельная функция с unit-тестом. Правила **общие**, не под конкретный документ.
- Размытые слова и обороты: «быстро», «удобно», «и т.п.», «и т.д.», «при необходимости»,
  «по возможности», «оптимально», «достаточно», «как правило», «в течение» без точки отсчёта.
- Незаполненное: «заполняются …», «TBD», «—» в значимом поле, «Да / Нет» без отметки,
  пустые строки таблиц согласования, отсутствующая версия/дата.
- Смешение единиц одной величины (тиын/тенге, копейки/рубли, сек/мс) в соседних требованиях.
- HTTP: метод `GET` у операции с глаголом «сохранить/создать/изменить/удалить»;
  код статуса упомянут в тексте, но не описан в списке статусов, и наоборот;
  `Content-Type` указан при «тело не используется»; тип поля в запросе ≠ типу в ответе.
- Ссылки на дочерние документы и разделы, которых нет в тексте.

## 7. Надёжность («сложно сломать»)

- `temperature=0`; ID модели и провайдер берутся из `.env`, в коде нет захардкоженных ID.
- Ретраи с экспоненциальным backoff (`tenacity`) на 429/5xx/таймаут; для 429 учитывается `retry-after`.
- **Кэш LLM** на диске (`.cache/llm/<sha256(provider+model+prompt)>.json`): повторный прогон
  воспроизводим и не тратит квоту. Флаг `--no-cache` его отключает.
- Абстракция провайдера (`reqcheck/llm/base.py`): `gemini` (по умолчанию), `openai_compat`
  (OpenAI/OpenRouter/Ollama), `fake` (для тестов, отвечает фикстурами).
- **Документ — это данные, а не инструкции.** Текст документа оборачивается в
  `<document>…</document>`, а в системном промпте явно сказано игнорировать любые инструкции внутри.
  Есть тест с документом, содержащим prompt injection.
- **Никакого хардкода под выданный документ.** Агент должен работать на любом ТЗ.
  Тестовые фикстуры содержат минимум два других документа.
- Нет ключа → режим `lint-only` с явной пометкой в паспорте и предупреждением в консоли.
- Коды выхода: 0 — ок; 2 — файл не найден или не поддерживается; 3 — пустой текст;
  4 — нет ключа при `--require-llm`; 5 — LLM недоступна после ретраев.
- Отчёт сначала пишется во временный файл, затем атомарно переименовывается.

## 8. Структура отчёта (порядок разделов фиксирован, проверяется `scripts/self_check.py`)

1. **Паспорт прогона**: название документа, путь, SHA-256, дата и время, провайдер и модель,
   версия агента (тег/коммит, пометка `dirty`), режим.
2. **Как агент нарезал требования**: таблица `ID в отчёте | ID в документе | Тип | Краткая формулировка | Цитата | Место`.
3. **Проверка каждого требования**: по каждому `R-xx` статус (✅ без замечаний / ⚠️ / ❌),
   затем замечания: критерий, серьёзность, цитата, место, проблема, как исправить.
4. **Проверка всего набора требований**: по каждому коду `S-*` вывод и замечания со ссылками.
5. **Уточняющие вопросы к аналитику**: сгруппированы по требованиям, у каждого вопроса
   ссылка на `R-xx`/`D-xxx` и пояснение, почему ответ нужен до разработки.
6. **Сводка**: число требований, замечаний по серьёзности и критериям, список критичных
   дефектов (непроверяемые / противоречивые / неполные), число отброшенных при проверке цитат.
7. **Итог**: вердикт (код считает по правилам: есть `critical` → «нельзя начинать без исправлений»;
   только `major` → «можно начинать с оговорками»; иначе «можно начинать») и
   «Что исправить в первую очередь»: топ-N, отсортированный по серьёзности и числу затронутых требований.
8. Приложение: методика и коды критериев со ссылками на пункты стандартов.

Правило §6 ТЗ: **никаких общих фраз без привязки к тексту.** Каждое замечание содержит
хотя бы одну прошедшую ground цитату и место.

```
reqcheck/

  ingest.py  segment.py  ground.py  render.py  pipeline.py
  checks/  each.py  set.py  lint.py

  prompts/ segment.md  check_each.md  check_set.md  repair.md
```

Стек: Python 3.11+, `google-genai`, `openai` (для openai_compat), `pydantic>=2`, `pymupdf`,
`python-docx`, `jinja2`, `tenacity`, `typer`, `rapidfuzz`, `python-dotenv`, `pytest`.

## 10. Правила работы в этом репозитории

- **Коммиты только от имени владельца репозитория** (берётся из `git config user.name/email`).
  **Не добавляй** в сообщения коммитов и PR строки `Co-Authored-By`, `Generated with`,
  ссылки на сессии и любые другие трейлеры или упоминания ассистента.
  Не меняй `git config` и не передавай `--author`.
- Сообщения коммитов на английском, в стиле Conventional Commits (`feat:`, `fix:`, `test:`, `docs:`),
  маленькими логическими шагами.
- Не коммить `.env`, ключи, `.cache/`. Перед коммитом запускай `pytest -q` и `python scripts/self_check.py --repo`.
- Не пиши отчёт вручную и не правь сгенерированный отчёт руками: только перегенерация.
- Не подгоняй код под конкретные формулировки выданного документа (никаких «если в тексте "Ф-3"…»).
  Если правило нужно, оно должно быть общим и иметь тест на другом документе.
- Промпты лежат в `reqcheck/prompts/*.md`, а не в строках кода.
- Если требование ТЗ организаторов и этот файл расходятся, прав ТЗ. Сообщи о расхождении.
