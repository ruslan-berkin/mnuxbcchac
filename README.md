# reqcheck: агент статической проверки требований

Агент читает документ с требованиями (PDF, DOCX, MD, TXT), выделяет отдельные требования и
проверяет каждое и весь набор по **ISO/IEC/IEEE 29148:2018** (п. 5.2.5, 5.2.6) и
**IEEE Std 830-1998** (п. 4.3). Результат — отчёт на русском в файле: паспорт прогона, таблица
нарезки, замечания к каждому требованию и к набору, **уточняющие вопросы аналитику**, сводка и вердикт
«можно ли начинать разработку».

Проект для BCC-HUB x MNU FinTech Hackathon. Задание: <https://github.com/BCC-HUB/ai-requirements-validator-task>.

## Для проверяющих

| Что | Где |
|---|---|
| Живой сайт | <https://sau-ai.onrender.com> (бесплатный тариф: после простоя первый ответ может идти около минуты) |
| Документ организаторов (вход агента, не результат) | [examples/input/requirements.md](examples/input/requirements.md), [PDF](examples/input/requirements.pdf) |
| Отчёт, сформированный агентом | [reports/report.md](reports/report.md), [JSON](reports/report.json), [журнал прогона](reports/report.log) |
| Запуск одной командой | `python -m reqcheck examples/input/requirements.pdf reports/report.md` |
| Как получить и куда положить ключ | раздел «Быстрый старт» ниже, шаблон [.env.example](.env.example) |
| Самопроверка отчёта и репозитория | `python scripts/self_check.py --report reports/report.md` и `--repo` |

Принцип: **LLM думает, код контролирует.** Модель только находит дефекты и формулирует замечания и
вопросы. Структуру отчёта, счётчики, вердикт, паспорт и проверку цитат делает детерминированный код.

## Быстрый старт

Нужен Python 3.11 или новее.

```bash
git clone https://github.com/ruslan-berkin/mnuxbcchac.git
cd mnuxbcchac
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt -c constraints.txt   # точные проверенные версии
```

### 1. Получите ключ LLM и положите его в `.env`

Скопируйте пример и впишите ключ и **точный ID модели** (ID моделей в коде не зашиты):

```bash
cp .env.example .env
```

| Провайдер | Где взять ключ | Переменные в `.env` |
|---|---|---|
| Google Gemini (есть бесплатный тариф) | <https://aistudio.google.com/> → *Get API key* | `GEMINI_API_KEY`, `GEMINI_MODEL` |
| Groq (OpenAI-совместимый API) | <https://console.groq.com/keys> | `GROQ_API_KEY`, `GROQ_MODEL` |
| OpenAI, OpenRouter, Ollama, vLLM и другие OpenAI-совместимые | у провайдера | `OPENAI_API_KEY`, `OPENAI_MODEL`, `OPENAI_BASE_URL` |

Провайдера по умолчанию задаёт `LLM_PROVIDER` (`gemini`, `groq` или `openai_compat`), либо флаг
`--provider`. Файл `.env` остаётся только на вашей машине: он в `.gitignore`. Ключи в репозиторий не
коммитятся, в корне лежит `.env.example` без ключей.

### 2. Запустите проверку одной командой

```bash
python -m reqcheck <путь_к_требованиям> <путь_к_отчёту.md>
```

Пример на документе организаторов:

```bash
python -m reqcheck examples/input/requirements.pdf reports/report.md --provider openai_compat
```

### 3. Куда ляжет отчёт

Рядом с отчётом всегда создаются три файла:

| Файл | Что внутри |
|---|---|
| `reports/report.md` | отчёт для человека (Markdown) |
| `reports/report.json` | те же данные, машиночитаемо |
| `reports/report.log` | ход прогона: вызовы LLM, отброшенные цитаты, слияния, перепроверки |

Отчёт сначала пишется во временный файл и затем атомарно переименовывается.

## Какая модель использована

Модель и провайдер записываются в **паспорт прогона** (раздел 1 отчёта) вместе с датой, SHA-256
входного файла и версией агента (тег или коммит; пометка `dirty`, если в дереве были правки).
Отчёт в `reports/report.md` получен моделью **`gpt-6.2-sol` (OpenAI, `openai_compat`)**, версия агента
`v1.3`. Агент проверен также на Gemini (`gemini-3.1-flash-lite`) и Groq (`openai/gpt-oss-120b`).
Модель выбирает команда: подойдёт любая, которая умеет отвечать JSON по схеме.

## Режим без ключа

Если ключа нет, агент **не падает**: он работает в режиме `lint-only` (только детерминированные правила,
без LLM), пишет предупреждение в консоль и помечает режим в паспорте. Принудительно этот режим включает
флаг `--lint-only`. Если ключ обязателен, используйте `--require-llm` (код выхода 4).

```bash
python -m reqcheck examples/input/requirements.pdf reports/report_lint.md --lint-only
```

## Опции командной строки

| Опция | Назначение |
|---|---|
| `--provider`, `--model` | провайдер и ID модели (иначе из `.env`) |
| `--lint-only` | только правила без LLM |
| `--require-llm` | ошибка, если нет ключа |
| `--no-cache` | не использовать кэш ответов LLM |
| `--workers N` | параллельных вызовов LLM (по умолчанию 4; `REQCHECK_WORKERS`) |
| `--no-fallback` | не переключаться на запасной провайдер |
| `--answers FILE` | перепроверить замечания с ответами аналитика (строки `D-013: ответ`): рядом с отчётом появятся `.recheck.md` и `.recheck.json`, вердикт «было → стало» считает код |

**Запасной провайдер.** Если основной недоступен (лимит, 5xx), агент сам переходит к другим провайдерам,
у которых заполнены ключ и модель (`LLM_FALLBACK=groq,gemini` задаёт порядок, `none` отключает).
**Кэш.** Ответы LLM лежат в `.cache/llm/`; повторный прогон того же документа не тратит квоту и даёт
тот же отчёт. **Коды выхода:** `0` ок; `1` внутренняя ошибка (текст без секретов, детали в `.log`); `2` файл не найден или формат не поддерживается; `3` в документе нет
текста (скан); `4` нет ключа при `--require-llm`; `5` LLM недоступна после ретраев; `6` исчерпан бюджет прогона
(число вызовов LLM, объём текста, время). Слишком большой документ даёт код `2`.

## Как устроен агент

```
ingest → segment → check_each ─┐
                   check_set  ─┼→ ground → consolidate → verify → questions → render
                   lint (без LLM)┘
```

| Этап | Модуль | Кто делает | Суть |
|---|---|---|---|
| ingest | `ingest.py` | код | PDF (`pymupdf`, таблицы как строки `\| a \| b \|`), DOCX, MD, TXT → блоки с якорями (страница, раздел, строка). Пустой текст — ошибка 3 |
| segment | `segment.py` | код + LLM | явные ID (`Ф-1`, `FR-2`, `REQ-3`) регулярками, остальные требования выделяет LLM; у каждого дословная цитата |
| check_each | `checks/each.py` | LLM | проверка требований батчами по 5 с контекстом раздела по закрытому списку кодов критериев |
| check_set | `checks/set.py` | LLM | четыре прохода: приёмка ↔ требования, правила и состояния, интерфейсы/данные/API, качество и выводы по `S-*` |
| lint | `checks/lint.py` | код | 16 правил без LLM: размытые слова, заглушки, пустые поля, единицы, ошибки HTTP, ссылки на несуществующее |
| ground | `ground.py` | код | каждая цитата нормализуется и ищется в тексте (точно, затем fuzzy ≥ 90). Выдуманная цитата — замечание отбрасывается и пишется в лог и счётчик |
| consolidate | `consolidate.py` | LLM + код | объединение смысловых дублей; группы проверяет код, цитаты и вопросы сохраняются |
| verify | `verify.py` | LLM | независимая перепроверка критичных замечаний и утверждений о противоречиях; ложные снимаются |
| questions | `questions.py` | LLM | вопрос к каждому critical/major, если модель его не дала |
| render | `render.py`, `templates/report.md.j2` | код | отчёт собирает Jinja2-шаблон, вердикт и приоритеты считает код |

**Надёжность.**
- Каждый ответ LLM проходит валидацию по схеме (pydantic); при ошибке один повторный запрос «исправь по схеме»,
  затем требование помечается «не проверено» в отчёте, а не молча теряется.
- `temperature=0` (если модель допускает), ретраи с экспоненциальным backoff на 429/5xx/таймаут, учёт `retry-after`.
- Документ в промпте обёрнут как данные в `<document>`, модель обязана игнорировать инструкции внутри него
  (есть тесты с prompt injection).
- Агент не заточен под выданный документ: правила общие, тесты идут на нескольких других документах.

Подробнее о принципах и модели данных: [CLAUDE.md](CLAUDE.md). План работ: [PLAN.md](PLAN.md).

## Лимиты и безопасность

Ядро защищено от больших и враждебных входов (важно, если агента вызывает сайт):

- **Лимиты ввода** (`reqcheck/limits.py`): размер файла, число страниц, символов, строк, требований и замечаний.
  По умолчанию щадящие для CLI; `Limits.web()` даёт жёсткие значения для публичного сайта. Любой лимит
  переопределяется переменной `REQCHECK_<ИМЯ>` (например, `REQCHECK_MAX_PAGES=100`). Перед разбором проверяются сигнатура файла
  и размер DOCX после распаковки (защита от zip-бомб).
- **Изоляция парсера:** PDF и DOCX разбираются в отдельном процессе с таймаутом (`REQCHECK_PARSE_TIMEOUT_S`), лимитом памяти и
  CPU и окружением без API-ключей. DOCX: колонтитулы, сноски и текстовые рамки не читаются, об этом есть предупреждение
  и пометка «проверка неполная». Отключить песочницу для отладки: `REQCHECK_SANDBOX=0`.
- **Файлы отчёта:** старые `.md` и `.json` удаляются при старте нового прогона (после проверки входа), отчёт `.md` пишется
  последним: если он есть, прогон завершился.
- **Бюджет прогона:** потолок числа вызовов LLM, объёма отправленного текста и времени (`REQCHECK_MAX_LLM_CALLS`,
  `REQCHECK_MAX_PROMPT_CHARS`, `REQCHECK_DEADLINE_S`). Попадания в кэш бюджет не тратят. Параллельность не больше 8 потоков.
- **Документ — данные:** текст документа и всё, что из него получено (заголовки, цитаты, списки требований, ответы модели),
  подаётся в промпт в блоках `<document-XXXX>` / `<data-XXXX>`, где суффикс — хеш самого текста (подделать закрывающий тег нельзя);
  похожие на теги фрагменты обезвреживаются. Фрагменты, похожие на команды ИИ-ассистенту, детерминированно отмечаются
  замечанием, поэтому вердикт «можно начинать» при них невозможен.
- **Отчёт безопасен для вставки в страницу:** недоверенный текст экранируется (`\< \> \[ \]`), HTML и ссылки не образуются.
  На сайте всё равно рендерите с санитайзером и CSP.
- **Честный вердикт:** если часть проверки не выполнена (сбой этапа, не выделены требования, страницы без текста,
  много отброшенных цитат), вердикт никогда не «можно начинать», а «проверка неполная» с причинами в разделе 7.
- **Секреты** вырезаются из логов и текстов ошибок. Лог каждого прогона изолирован от других прогонов в том же процессе.

### Использование из кода (например, из веб-сервиса)

```python
from reqcheck.config import Settings
from reqcheck.limits import Limits
from reqcheck.pipeline import run

report = run(
    upload_path, work_dir / "report.md",           # отдельный каталог на запрос
    Settings("openai_compat", model, api_key),     # явные настройки, .env библиотекой не читается
    limits=Limits.web(),
    display_name=original_filename,                # в паспорт идёт только безопасное имя, не серверный путь
    cache_namespace=user_id,                       # либо use_cache=False
    workers=4,
)
```

Запасных провайдеров в сервисе включайте только осознанно (по умолчанию `LLM_FALLBACK=none`), иначе документ при сбое
основного уйдёт в другие сервисы. Ограничить модели можно списком `REQCHECK_MODEL_ALLOWLIST`.

## Сайт (sau.ai)

Веб-интерфейс поверх ядра: Next.js со статическим экспортом (`web/`) и FastAPI (`server/`), один контейнер.
Задание и порядок работ: [SITE.md](SITE.md).

```bash
docker build -t sau-site .
docker run -p 8000:8000 -e LLM_PROVIDER=openai_compat -e OPENAI_API_KEY=... -e OPENAI_MODEL=... sau-site
```

Без ключа работают лендинг и пример; живые прогоны, чат и перепроверка требуют ключа. Лимиты платного ключа
задаются переменными: `SITE_LIVE` (0 выключает живые прогоны), `SITE_DAILY_RUNS` (5, на Render 20), `SITE_RUNS_PER_IP` (1, на Render 5),
`SITE_CHAT_PER_IP` (40), `SITE_RECHECK_PER_IP` (5), `SITE_DAILY_CHAT` (300), `SITE_DAILY_RECHECK` (40),
`SITE_MAX_CHAT_TOKENS` (1500). Локально без Docker: `SITE_DOTENV=1 uvicorn server.main:app` (читает `.env`).

### Деплой на Render

1. Render → **New → Blueprint** → этот репозиторий (`render.yaml`: Docker, free, health check `/api/health`).
2. В кабинете вписать `OPENAI_API_KEY` и `OPENAI_MODEL`. Лимиты уже заданы в `render.yaml`.
3. В кабинете OpenAI поставить **жёсткий месячный лимит расходов**.
4. Бесплатный сервис засыпает: перед демо открыть `/api/health` и дождаться ответа (около минуты).

Референс дизайна в `design/teal-treasury-landing.tsx`: шаблон «Teal Treasury Landing» (MIT, Kedhareswer Naidu).

## Структура отчёта

1. Паспорт прогона. 2. Как агент нарезал требования. 3. Проверка каждого требования.
4. Проверка всего набора. 5. Уточняющие вопросы к аналитику. 6. Сводка. 7. Итог (вердикт и «что исправить
в первую очередь»). 8. Приложение: методика и коды критериев со ссылками на пункты стандартов.

Вердикт считает код: есть `critical` → «нельзя начинать без исправлений»; только `major` → «можно начинать
с оговорками»; иначе «можно начинать».

## Тесты и самопроверка

```bash
python -m pytest                                          # без ключа, на фейковой LLM
python scripts/self_check.py --repo                       # проверка репозитория
python scripts/self_check.py --report reports/report.md   # проверка отчёта на соответствие ТЗ
```

CI (`.github/workflows/ci.yml`) запускает `pytest`, прогон на примере без ключа и `self_check`.

## Ограничения

- Агент проверяет формулировки, а не запускает программу: это ревью требований до разработки.
- Качество замечаний зависит от модели. Слабые модели чаще дают дубли и ложные срабатывания; перепроверка и
  консолидация это уменьшают, но не исключают. Без кэша результат LLM может отличаться между прогонами
  даже при `temperature=0`; воспроизводимость обеспечивает кэш.
- PDF должен иметь текстовый слой. Сканы без распознавания агент отклоняет с кодом 3.
- Таблицы в PDF распознаются по границам ячеек; таблицы без рамок читаются как обычный текст.
- Бесплатные тарифы могут быть перегружены или ограничены по токенам в минуту: Groq (бесплатный)
  не вмещает весь документ в один запрос, Gemini иногда отвечает 503. Для этого есть ретраи, кэш и запасной провайдер.
- Полный прогон документа организаторов занимает около 4 минут на `gpt-6.2-sol` (4 потока) и стоит порядка
  десятков центов; повтор с кэшем занимает секунды.
