Место: стр. 1, раздел «Дизайн процесса UI», строки 19–20.

- **D-002** · `UNA` Однозначное · существенное (major)
  - Цитата: «На экране видны переключатель, поле «Порог, ₸», сумма за месяц и кнопка «Сохранить».»
  - Место: стр. 1, раздел «Дизайн процесса UI», строки 19–20
  - Проблема: Не определено, за какой период показывается сумма. Например, текущий календарный месяц и последние 30 дней дадут разные результаты для операций на границе месяца.
  - Как исправить: Указать период расчёта суммы и его границы.

### R-05: ⚠️ есть замечания

> «При ошибке ввода сообщение появляется под полем.»

Место: стр. 1, раздел «Дизайн процесса UI», строка 20.

- **D-003** · `CMP` Полное · существенное (major)
  - Цитата: «При ошибке ввода сообщение появляется под полем.»
  - Место: стр. 1, раздел «Дизайн процесса UI», строка 20
  - Проблема: Не указано, какие значения поля «Порог, ₸» считаются ошибочными. Нельзя определить, должно ли появляться сообщение при пустом поле, нуле или дробной сумме.
  - Как исправить: Задать правила проверки поля «Порог, ₸»: обязательность заполнения, допустимый диапазон и допустимость дробных значений.

- **D-005** · `UNA` Однозначное · существенное (major)
  - Цитата: «При ошибке ввода сообщение появляется под полем.»
  - Место: стр. 1, раздел «Дизайн процесса UI», строка 20
  - Проблема: Не указано, какое действие запускает проверку. По тексту нельзя определить, должно ли сообщение появиться до нажатия кнопки «Сохранить».
  - Как исправить: Указать событие, после которого при недопустимом значении появляется сообщение под полем.

### R-06: ⚠️ есть замечания

> «Проведение покупки → пересчёт расходов → проверка порога → при достижении отправка push → завершение.»

Место: стр. 1, раздел «BPMN схема процесса», строки 23–24.

- **D-006** · `CMP` Полное · существенное (major)
  - Цитата: «Проведение покупки → пересчёт расходов → проверка порога → при достижении отправка push → завершение.»
  - Место: стр. 1, раздел «BPMN схема процесса», строки 23–24
  - Проблема: Не определено, какие покупки и за какой период входят в сумму расходов, сравниваемую с порогом. Для одной и той же истории покупок разные правила отбора могут дать разные результаты проверки порога.
  - Как исправить: Задать состав покупок, включаемых в сумму, и границы расчётного периода либо сослаться на правило расчёта, которое их определяет.

- **D-007** · `UNA` Однозначное · существенное (major)
  - Цитата: «Проведение покупки → пересчёт расходов → проверка порога → при достижении отправка push → завершение.»
  - Место: стр. 1, раздел «BPMN схема процесса», строки 23–24

  - Проблема: Для требований не указаны приоритеты и устойчивость. Набор не показывает, можно ли отложить отдельные требования и какие правила ещё могут измениться до реализации.
  - Как исправить: Указать для каждого требования приоритет и признак устойчивости. Если все требования обязательны для одного выпуска, зафиксировать это общим правилом и отдельно отметить требования, ожидающие пересмотра.

### S-MOD: Модифицируемый

Вывод: Версия и дата комплекта не зафиксированы, история изменений отсутствует. Нельзя установить, какие редакции частей A и B образуют одну согласованную версию.

- **D-036** · `S-MOD` Модифицируемый · существенное (major)
  - Требования: набор в целом
  - Цитата: «Документ (версия/дата) в источнике не заполнен.»; «Часть B — дочерняя спецификация, на которую ссылается раздел интеграции в части A.»; «Уведомление о расходах по карте»
  - Место: стр. 2, раздел «Ревью требований», строка 56; стр. 1, раздел «Уведомление о расходах по карте», строка 3; стр. 1, раздел «Уведомление о расходах по карте», строка 1
  - Проблема: Версия и дата не заполнены, история изменений отсутствует. После правки одной части нельзя определить, какая редакция второй части соответствует изменённому комплекту. Тот же дефект затрагивает критерии: S-CMP.
  - Как исправить: Присвоить комплекту версию и дату, зафиксировать входящие в него редакции частей A и B и вести журнал изменений с указанием затронутых разделов.

  - Как исправить: Для каждого критерия приёмки указать идентификатор или ссылку на проверяющий его тест и место фиксации результата.

Добавить критерий приёмки для этого сценария. (стр. 1, раздел «Функциональные требования», строка 32; стр. 1, раздел «Функциональные требования», строки 33–34)

## 8. Приложение. Методика и коды критериев

Проверка выполняется по ISO/IEC/IEEE 29148:2018 (п. 5.2.5 и 5.2.6) и IEEE Std 830-1998 (п. 4.3). Модель только находит дефекты и формулирует замечания; структуру отчёта, счётчики, вердикт и проверку цитат выполняет код.

### Отдельное требование

| Код | Критерий | Пункт стандарта | Как проверять |
| :--- | :--- | :--- | :--- |
| `NEC` | Необходимое | ISO/IEC/IEEE 29148:2018, п. 5.2.5 | Требование нужно для достижения цели, без него чего-то не хватает; лишнее и дублирующее отмечается. |
| `APP` | Уместное, без лишних проектных решений | ISO/IEC/IEEE 29148:2018, п. 5.2.5 | Описывает что нужно, а не как делать: нет навязанных технологий, таблиц, алгоритмов без причины. |
| `UNA` | Однозначное | ISO/IEC/IEEE 29148:2018, п. 5.2.5; IEEE Std 830-1998, п. 4.3.2 | Допускает ровно одно толкование; нет размытых слов, неопределённых ссылок и не заданных границ. |
| `CMP` | Полное | ISO/IEC/IEEE 29148:2018, п. 5.2.5; IEEE Std 830-1998, п. 4.3.3 | Можно реализовать и проверить без догадок: заданы условия, значения, единицы, границы и исключения. |
| `SNG` | Единичное | ISO/IEC/IEEE 29148:2018, п. 5.2.5 | Содержит одно требование; склеенные «и/или» и несколько обязанностей в одной фразе отмечаются. |
| `FEA` | Выполнимое | ISO/IEC/IEEE 29148:2018, п. 5.2.5 | Реализуемо в известных ограничениях по технологии, срокам и бюджету, не противоречит физике и данным. |
| `VER` | Проверяемое | ISO/IEC/IEEE 29148:2018, п. 5.2.5; IEEE Std 830-1998, п. 4.3.6 | По требованию можно написать тест с однозначным критерием «выполнено / не выполнено». |
| `COR` | Корректное | ISO/IEC/IEEE 29148:2018, п. 5.2.5; IEEE Std 830-1998, п. 4.3.1 | Верно отражает потребность заинтересованных сторон и не содержит фактических ошибок. |
| `CNF` | Соответствует шаблону и стандарту | ISO/IEC/IEEE 29148:2018, п. 5.2.5 | Оформлено по принятому шаблону: идентификатор, формулировка, обязательные поля заполнены. |

### Набор требований

| Код | Критерий | Пункт стандарта | Как проверять |
| :--- | :--- | :--- | :--- |
| `S-CMP` | Набор полный | ISO/IEC/IEEE 29148:2018, п. 5.2.6; IEEE Std 830-1998, п. 4.3.3 | Нет пропусков: покрыты все цели, сценарии, ошибки, данные, интерфейсы и критерии приёмки. |
| `S-CON` | Набор непротиворечивый | ISO/IEC/IEEE 29148:2018, п. 5.2.6; IEEE Std 830-1998, п. 4.3.4 | Требования, критерии приёмки, данные и API не противоречат друг другу; термины и единицы едины. |
| `S-FEA` | Набор выполнимый | ISO/IEC/IEEE 29148:2018, п. 5.2.6 | Требования можно выполнить одновременно в заданных ограничениях. |

| `S-TRC` | Трассируемый | IEEE Std 830-1998, п. 4.3.8 | Есть идентификаторы и связи цель → требование → критерий приёмки → тест; ссылки ведут к существующим разделам. |

### Серьёзность

- `critical`: непроверяемое, противоречивое или неполное так, что без исправления нельзя написать код или тест.
- `major`: несколько разумных трактовок, отсутствует граница или единица.
- `minor`: стиль, шаблон, оформление, незаполненные служебные поля.
